## 最值得学习的做法

1. 每账号任务锁、重复启动抑制、完成回调和显式连接状态机。多账号之前，单账号生命周期也值得采用。
2. 平台轮询的“进行中请求合并 + 短 TTL 缓存 + 限流结果延长 TTL”，可降低请求风暴。
3. 账号级令牌桶、熔断器与退避。它比只依赖 Worker 重试更接近平台运行保护。
4. 发货前在锁内二次核对商品、账号、买家、订单归属和待发货状态。
5. 多份卡密必须全部取得且全部发送才继续；发生部分成功就停止重试并转人工。这个思想与 `RESULT_UNKNOWN` 一致。
6. 用户/账号/商品三级保护规则、优先级与商品排除，以及危险批处理默认 `dry_run`。
7. AI 输出先做长度、思维链和确定性价格后校验，不把提示词当安全边界。
8. SQLite 在线一致性备份和滚动保留，以及更高密度的运营日志与时间筛选。

## 明确不能照搬

1. 上游默认 `0.0.0.0` 和公开端口映射；本项目必须保持 `127.0.0.1`。
2. 完整 Cookie、账号密码返回前端或写入备份；本项目不实现 Cookie 导出。
3. 明文闲鱼密码、无盐后台密码、默认 `admin/admin123` 和纯内存会话。
4. `_m_h5_tk`、MD5 私有签名和卖家端 `mtop.*` 接口。
5. 隐藏 `navigator.webdriver`、拟人轨迹、自动滑块训练和 Cookie 回写。
6. 直接 WebSocket 发卡密/调用确认发货，绕过策略、Outbox 和扩展证据链。
7. 保护规则读取或执行异常时“按放行处理”。安全规则必须失败关闭。
8. 运行时原地 `ALTER TABLE`、迁移失败仍启动、容器 root 与 `chmod 777`。

## 本工作台独有优势

- 可见页面和账号指纹绑定，不把 Cookie 当应用数据。
- 草稿填充与最终发布是两个动作、两次审批。
- 动作批准后仍复核标签页、页面类型、DOM、账号、买家最新消息和订单金额。
- 外部成功必须有本次动作的新业务证据；缺证据即 `RESULT_UNKNOWN`，不把“按钮点过”当成功。
- 平台验证出现时在任何写入前失败关闭，不尝试绕过。
- 24 个商品的内容、六图、价格底线、许可证、交付包和 SHA-256 形成一个可审计链路。
- 客户同意、远程服务摘要、退款人工、强风险分类和数据保留被建成产品能力，而不是操作员口头约定。
- 测试、文档和界面会区分模拟、真实只读、真实写入证据，不用演示数据冒充经营结果。

## 五种方法再次审视

### 第一性原理

真实经营的最小闭环不是“功能菜单多”，而是：正确识别当前账号和目标 → 依据已核验内容作决定 → 经授权只执行一次 → 得到可归因的业务结果 → 不确定时停止并交人。当前本项目已经较好覆盖前四个软件条件，但真实平台上的“只执行一次并取得结果证据”还没有完成受控实机证明。

### 对抗式审查

| 攻击/故障假设 | 当前防线 | 结论 |
|---|---|---|
| 审批后切换会话或买家追加消息 | 执行前重取目标和最新入站正文 | 通过自动测试 |
| 点击成功但网络断开 | 需要新的动作级业务证据，否则封存 | 通过自动测试 |
| 进程在外部动作中间崩溃 | 启动时把执行中浏览器动作隔离为未知并暂停 | 通过代码和测试，仍需实机观察 |
| 操作员误恢复全局写入 | PIN 与未知结果确认窗口 | 本轮已修复并人工体验 |
| Codex 越界读取其他订单 | 订单 Codex 失败关闭 | 风险已止血，功能尚未实现 |
| 备份文件被拷走离线猜 PIN | 仅 scrypt + 6–12 位数字 PIN | 未解决，生产阻断 |
| 闲鱼 DOM 或验证流程变化 | 绑定过期、字段缺失或验证出现即失败关闭 | 安全正确，但可用性仍需真实订单校准 |
| UI 文案让用户误以为已自动化 | 能力文案已按实现校正 | 本轮已修复 |

### 苏格拉底式自问

- 测试全绿是否等于可真实投产？不等于；平台页面、账号和受控买家仍是外部事实。
- 功能比对照项目少是否就是落后？不是；不安全的自动化不应计为完成度。
- 失败关闭是否会降低自动化率？会，但它把无法证明的成功转换成明确人工待办，代价可控。
- 现在最小的真实下一步是什么？不是批量发布，而是一件低风险商品的只填草稿、一次人工核对和一个受控测试买家。
- 是否应立刻做多账号和卡密库存？在单账号真实闭环没有通过前，不应扩大状态空间。

### 头脑风暴后的优先级

P0：设计高熵恢复密钥/独立备份口令并做恢复演练；完成单件草稿、发布、FAQ 回复、订单识别和交付的受控实机证据；补真实卖家订单适配。  
P1：正式安装包、签名更新与回滚；账号级限流/熔断；轮询请求合并；发布运行手册、健康指标和恢复演练记录；实现真正的单订单 Codex 工作区和审批白名单。  
P2：只有业务量证明需要后再做多账号、卡密库存、批量商品自动化、深色主题和更复杂的 AI 记忆。

### 奥卡姆剃刀

保留：单账号、可见浏览器、持久 Outbox、确定性 FAQ、人工审批、固定数字包。  
暂缓：多账号、私有协议、自动验证、复杂 AI 客服、无人值守批量互动。  
原因：前者足以验证真实商业闭环，后者会同时放大账号风险、隐私范围、状态组合和故障恢复成本。

| 使用层级 | 状态 | 说明 |
|---|---|---|
| 本地内容制作、六图、商品准备、模拟经营 | 可用 | 全链路已实际体验并通过自动测试 |

| 单件受控写入试运行 | 有条件可进入 | 需要用户准备测试商品与测试买家，逐步完成草稿、发布、回复、订单和交付 |
| 真实账号无人值守生产 | 不可放行 | 缺少受控实机闭环、真实订单适配、强备份恢复方案和生产运行证据 |
